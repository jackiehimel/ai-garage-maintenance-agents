# Maintenance library: implementation research and recommended build approach

Prepared for Jackie, 2026-10-27. This document covers the 9 agents currently published in AI Garage. It recommends how to build them; it does not change their approved scope, the site, or the backlog.

## Recommendation

Build one small maintenance toolkit with 9 specialist workflows. Reuse existing scanners, browser runners, artifact parsers and investigation engines through their supported interfaces. Solvd should own the application expectations, evidence history, comparisons, prioritization, reviewed handoff and later verification. Those pieces turn individual tool results into a repeatable maintenance service.

Use AI where it helps interpret evidence, investigate within agreed access, connect a change to application context, or draft a reviewable action plan. Keep measurements, assertions, policy records, finding identity and execution status deterministic. An unavailable model should leave a useful evidence package rather than erase the run.

Keep this a standalone maintenance offering. The selected Cascade/Actions execution direction can call the toolkit through thin input/output adapters. No future ADLC product, access to QE-owned agents, Kubernetes deployment, new security portfolio platform or hosted monitoring subscription is required for the first version. Reuse an existing customer's tools when they already provide the needed evidence.

The core comparison covers 25 public implementation repositories, including native tools, concrete service implementations, AI investigation/review systems and workflow examples, supplemented by downstream usage configurations. Selected entrypoints, core logic, tests, workflow definitions and license files were inspected at pinned commits. This supports assembly recommendations, not measured accuracy, cost, time savings or production readiness. Detailed source records are linked at the end.

“Starting point” means an implementation seam to validate and integrate, not a recommendation to install every project in the row. In particular, the browser roles can share approved state setup while keeping their distinct checks and results.

## 1. Reliability & Incident Triage

**How the implementations differ.** Robusta receives events, executes configured enrichment actions, builds findings and routes them to sinks. HolmesGPT implements an actual bounded model/tool investigation loop over enabled telemetry connectors. K8sGPT runs Kubernetes analyzers and can add AI explanations afterwards. These solve different parts of incident work. [Robusta event/enrichment path](https://github.com/robusta-dev/robusta/blob/ebb6267546b94e7578e51f8191113f2376d9fc7a/src/robusta/core/playbooks/playbooks_event_handler_impl.py#L230-L332), [Holmes investigation loop](https://github.com/HolmesGPT/holmesgpt/blob/49804bde566633d4e945952e01c6bf99df6df7ab/holmes/core/tool_calling_llm.py#L1260-L1305), [K8sGPT analyze command](https://github.com/k8sgpt-ai/k8sgpt/blob/d77b5357a309a26abd9055fdd768b284f657313c/cmd/analyze/analyze.go#L50-L125).

**What to adopt.** Start with existing availability/certificate/job signals and approved logs or exported incident evidence. Adapt Robusta's structured finding/enrichment boundary and its JSON file-output approach. Introduce Holmes investigation only when the application has useful telemetry and explicitly scoped read connectors. Prefer invoking a selected released interface over coupling to internal Python classes. [Robusta structured file output](https://github.com/robusta-dev/robusta/blob/ebb6267546b94e7578e51f8191113f2376d9fc7a/src/robusta/core/sinks/file/file_sink.py#L10-L33), [Holmes enabled tool registration](https://github.com/HolmesGPT/holmesgpt/blob/49804bde566633d4e945952e01c6bf99df6df7ab/holmes/core/tools_utils/tool_executor.py#L60-L107).

**What Solvd adds.** Connect the event to the affected application function, evidence timeline, recent supplied changes, accountable owner and a checkable next step. Preserve hypotheses as hypotheses. An actual job-completion check needs a heartbeat or downstream outcome: K8sGPT's CronJob analyzer inspects configuration conditions, which does not establish that the business task completed. [CronJob analyzer](https://github.com/k8sgpt-ai/k8sgpt/blob/d77b5357a309a26abd9055fdd768b284f657313c/pkg/analyzer/cronjob.go#L29-L136).

**First proof.** Feed one known incident and one stale/missing-data case through the workflow. Require source-linked observations, honest unknowns and owner/action output. The lighter initial build is evidence intake and enrichment; open-ended investigation and new observability integrations require more work. Retain native urgent monitoring rather than making a reviewed report the paging mechanism.

## 2. Security & Lifecycle Review

**How the implementations differ.** OSV-Scanner extracts an inventory and matches advisory data. Dependency-Track maintains projects/SBOMs and schedules vulnerability, policy and metrics analysis across a portfolio. oasdiff compares two OpenAPI specifications with deterministic compatibility rules. An advisory scanner, a portfolio database and an interface comparator are complementary engines. [OSV pipeline](https://github.com/google/osv-scanner/blob/8748c7ca24ecb3fb35a1319c983f41b4a6cf5833/pkg/osvscanner/osvscanner.go#L117-L167), [Dependency-Track workflow](https://github.com/DependencyTrack/dependency-track/blob/e1e3c8f0189bd445a0f09cc90d211afd2a681d8f/apiserver/src/main/java/org/dependencytrack/analysis/AnalyzeProjectWorkflow.java#L42-L115), [oasdiff checker](https://github.com/oasdiff/oasdiff/blob/a4ba100f880c7579765c5e63915a99bf1acc6967/checker/checker.go#L10-L64).

**What to adopt.** Use OSV's machine-readable results for approved lockfiles/SBOMs. Read an existing Dependency-Track instance where available; operating a new instance should follow a demonstrated portfolio need. Use local oasdiff output for authoritative old/new API specifications. Borrow the owned, expiring exception pattern visible in RxJS's actual OSV workflow. [RxJS exception/artifact workflow](https://github.com/ReactiveX/rxjs/blob/54796b38a57e6309f9861e174737479bb3f63f61/.github/workflows/osv.yml#L1-L53).

**What Solvd adds.** Link inventory/advisories to supplied deployment evidence, affected functionality, official vendor/runtime notices, action deadlines, owners and reviewed deferrals. AI can help interpret a notice and propose its application mapping; uncertain applicability stays visible. Source inventory alone cannot establish deployed exposure.

**First proof.** An inventory with a known advisory, a fixed version, an expiring exception and an unresolved deployment mapping. Separately compare a deliberately breaking API change. The initial scanner adapter is relatively small; application/vendor mapping is the harder continuing work. Explicitly choose analysis modes: OSV documents default Go call analysis and opt-in Rust analysis that executes dependency build scripts. The first inventory-review slice should disable unwanted analysis and omit fix/build operations. [Mode behavior](https://github.com/google/osv-scanner/blob/8748c7ca24ecb3fb35a1319c983f41b4a6cf5833/docs/scan-source.md#L142-L190).

## 3. Functional & Integration QA

**How the implementations differ.** Playwright supplies the browser/API runner, assertions, attempts and attachments. Upright wraps probes in a scheduled service with persisted results, timeouts, cleanup and stale-job handling. Checkly's demo shows test selection for scheduled monitoring and separate stateful integration suites. [Playwright result serialization](https://github.com/microsoft/playwright/blob/a169686c61af856cd1434b4994ef9c3222ee1041/packages/playwright/src/reporters/json.ts#L186-L231), [Upright job lifecycle](https://github.com/basecamp/upright/blob/a40363fe71c2f1887be444b8864478d083220365/app/jobs/upright/probe_check_job.rb#L1-L25), [Checkly suite selection](https://github.com/checkly/playwright-reporter-demo/blob/3c6bbead32723121bd4a989d4dc0d199249decc6/checkly.config.ts#L17-L49).

**What to adopt.** Run existing approved Playwright tests through its supported reporter interface. Adapt Upright's stale-work/time-limit/cleanup handling without taking on its entire Rails stack. Use Checkly's separation of safe monitoring selections and sandbox-only write tests. Its checkout example checks a downstream stock change and reads the created order back, a useful pattern for verifying an outcome beyond a successful click or response. [Checkout assertions/readback](https://github.com/checkly/playwright-reporter-demo/blob/3c6bbead32723121bd4a989d4dc0d199249decc6/tests/checkout.spec.ts#L10-L65).

**What Solvd adds.** Customer-approved tasks and outcomes, permitted accounts/actions, correlation to downstream processing, coverage and clear failure classification. Preserve every retry and distinguish application failures, blocked prerequisites, skipped tests and execution errors. AI may help group failures and propose a test repair; changes to the test and its permitted behavior remain reviewed.

**First proof.** One approved sandbox task with an independently checked API/downstream outcome, a deliberate integration failure and a missing-credential case. This works without QE's agents. Reusing a good existing suite is a smaller build; authoring reliable application-specific outcomes and fixtures is the slower part. A hosted monitoring account is optional.

## 4. Change & Release Review

**How the implementations differ.** PR-Agent already handles diff parsing, context limits, model review and structured/local output. gh-aw supplies executable workflow and controlled-output infrastructure; agentics supplies concrete workflow definitions and review instructions. The latter is a useful example but does not make a model's approval an independent release decision. [PR-Agent local mode](https://github.com/The-PR-Agent/pr-agent/blob/dff634a9ed1832970f6322ff5e0b6236934a0ba4/pr_agent/cli.py#L164-L174), [gh-aw output-job assembly](https://github.com/github/gh-aw/blob/0627fdbe4beb5f3b71aa569f8d97150b87f2111a/pkg/workflow/compiler_safe_outputs_job.go#L114-L227), [agentics review workflow](https://github.com/githubnext/agentics/blob/139fa09ef17cde4135e696ff8e7af09bc5ddfa6e/workflows/grumpy-reviewer.md#L57-L132).

**What to adopt.** Start with supplied diff/local JSON output, so a hosted PR integration is optional. PR-Agent's provider can additionally read matching working-tree files beneath a detected repository root. Use a controlled patch-only directory without `.git`, or explicitly approve and identify the repository/revision used for enrichment. [Context enrichment/fallback](https://github.com/The-PR-Agent/pr-agent/blob/dff634a9ed1832970f6322ff5e0b6236934a0ba4/pr_agent/git_providers/plain_diff_provider.py#L63-L105).

The local mode intentionally sets `publish_output=true` because publication means local stdout/file output. Disable external sinks, unrelated commands and automatic approval in both local and hosted modes. Hosted PR-URL review additionally disables hosted publication. Configured sinks run before the publication gate, so that flag alone is insufficient. [Local output](https://github.com/The-PR-Agent/pr-agent/blob/dff634a9ed1832970f6322ff5e0b6236934a0ba4/pr_agent/git_providers/plain_diff_provider.py#L123-L156), [sink-before-publication path](https://github.com/The-PR-Agent/pr-agent/blob/dff634a9ed1832970f6322ff5e0b6236934a0ba4/pr_agent/tools/pr_reviewer.py#L377-L402).

Retain the approved role's read-only Git history and existing language-tool evidence for supported duplication, complexity, architecture-boundary and contextual hotspot observations. Choose and validate those deterministic adapters for the pilot's declared languages. PR-Agent is a partial reviewer path: patch-only input cannot supply missing history or invent repository-wide structural observations. Unavailable history and unsupported languages remain coverage gaps. The approved inputs and method are recorded in [the current library source](/Users/jackiehimel/ai-garage-web/data/maintenance-agents.json).

**What Solvd adds.** A change plan tied to the original maintenance finding, intended acceptance criteria, exact source/head, relevant test and scan evidence, unreviewed diff coverage, rollback information and the human disposition. Adopt gh-aw's separate output processor concept within the accepted runtime; its staged preview is a preview, so the reviewer and permitted target/revision must be recorded separately. [Staged-output behavior](https://github.com/github/gh-aw/blob/0627fdbe4beb5f3b71aa569f8d97150b87f2111a/actions/setup/js/safe_output_processor.cjs#L62-L105).

**First proof.** Review a supplied maintenance patch with one known issue, partial context and a deliberately stale test artifact. Require the report to show the stale/missing evidence and avoid inferring release readiness from the model review. Local review plumbing is a smaller build; reliable change planning and readiness aggregation are more substantial.

## 5. Performance Regression

**How the implementations differ.** Lighthouse CI repeatedly measures page navigations and evaluates budgets. sitespeed.io supports controlled scripts, richer comparison output and a distinct diagnostic profiling run. Its documented interaction path explicitly starts measurement, clicks and stops measurement to collect a named synthetic interaction's INP. [LHCI collection](https://github.com/GoogleChrome/lighthouse-ci/blob/85d33432a9149033b62c69f11c6fe6da0e12e679/packages/cli/src/collect/collect.js#L87-L146), [sitespeed separate profile run](https://github.com/sitespeedio/sitespeed.io/blob/2371e74c55aeeb9179de941a940a8bfdadc02bf2/lib/plugins/browsertime/analyzer.js#L80-L116), [interaction example](https://github.com/sitespeedio/sitespeed.io/blob/2371e74c55aeeb9179de941a940a8bfdadc02bf2/docs/documentation/sitespeed.io/scripting/examples/index.md#L52-L80).

**What to adopt.** Begin with isolated LHCI navigation measurements, private raw results, explicit metrics and aggregation. Its assertion default is optimistic, and its representative run is selected around FCP/interactive medians, so neither should silently become our “median result.” Adopt sitespeed's separation of timed measurement and profiling when interactions or diagnostic depth justify the heavier runtime. [Assertion policy/default](https://github.com/GoogleChrome/lighthouse-ci/blob/85d33432a9149033b62c69f11c6fe6da0e12e679/packages/utils/src/assertions.js#L81-L98), [default aggregation](https://github.com/GoogleChrome/lighthouse-ci/blob/85d33432a9149033b62c69f11c6fe6da0e12e679/packages/utils/src/assertions.js#L164-L170), [representative-run selection](https://github.com/GoogleChrome/lighthouse-ci/blob/85d33432a9149033b62c69f11c6fe6da0e12e679/packages/utils/src/representative-runs.js#L17-L64).

**What Solvd adds.** Accepted comparable baselines with the same target/state, browser/engine, device/network/CPU, cache/auth and configuration; explicit noise/materiality decisions; preserved failed attempts and missing metrics. AI can connect a measured shift to traces/assets and supplied changes as an investigation hypothesis. Navigation TBT, scripted interaction INP and real-user distributions need separate labels.

**First proof.** Known slow/fast fixtures plus a changed browser/configuration and a missing metric. A configuration change must become “not comparable.” The navigation adapter is smaller; statistically useful customer baselines and interaction coverage require more work and execution time.

## 6. Accessibility Regression

**How the implementations differ.** The official axe Playwright adapter scans an already-open, explicitly configured page and returns full axe results. Pa11y CI orchestrates a URL queue and reports threshold-based outcomes. a11y-agent-skills adds finding fingerprints, changed/uncertain comparisons, keyboard assertions and repair verification. [Official adapter](https://github.com/dequelabs/axe-core-npm/blob/794589bda678dcc8d7d9d4246240f5d816e5613c/packages/playwright/src/index.ts#L151-L179), [Pa11y threshold handling](https://github.com/pa11y/pa11y-ci/blob/1c43bdcac7e4c7a66cdf48acf9e66ff7807b2c8e/lib/pa11y-ci.js#L95-L107), [finding lifecycle](https://github.com/smukh/a11y-agent-skills/blob/8bc24f049734c607e23bd3955700fd4858649614/packages/core/src/compare.ts#L45-L118).

**What to adopt.** Use official axe on approved Playwright states. Adapt a11y-agent-skills' finding identity, moved-target uncertainty and repair witness ideas. Strengthen its comparison signature with origin, browser/engine versions, auth and state-contract identity. Its normalizer retains violations but omits actual axe incomplete results; keep those explicitly. Pa11y's allowed count is useful for a simple gate but cannot establish which defects are new or fixed. [Repair witness](https://github.com/smukh/a11y-agent-skills/blob/8bc24f049734c607e23bd3955700fd4858649614/packages/core/src/verify.ts#L85-L147), [normalization gap](https://github.com/smukh/a11y-agent-skills/blob/8bc24f049734c607e23bd3955700fd4858649614/packages/core/src/normalize.ts#L84-L121), [comparison identity](https://github.com/smukh/a11y-agent-skills/blob/8bc24f049734c607e23bd3955700fd4858649614/packages/core/src/compare.ts#L11-L20).

**What Solvd adds.** Coverage by component/state, reproducible barriers, incomplete findings, accepted exceptions, outstanding keyboard/screen-reader review and rechecks of supplied repairs. AI can propose component grouping and explain consequences; a zero-violation scan does not establish conformance.

**First proof.** Broken/repaired modal or form states, an inaccessible frame and a moved selector. Prevent missing coverage or a lower issue count from becoming “fixed.” Automated collection is a smaller extension to approved browser fixtures; dependable state coverage and human review remain more work.

## 7. Technical SEO & Discoverability

**How the implementations differ.** nurkamol/seo-audit performs a concrete HTTP crawl, parses source HTML, runs checks and compares findings. Lighthouse supplies rendered artifacts and selected page audits. They observe different representations of a page. [Crawler entry/collection](https://github.com/nurkamol/seo-audit/blob/b70b3bf8f29bcbbdcdfb969079fd41097d1368e1/src/audit.mjs#L200-L258), [Lighthouse gather/audit split](https://github.com/GoogleChrome/lighthouse/blob/1a4ffa418258919adbbf6ccca548c02e0092bafd/core/index.js#L39-L81).

**What to adopt.** A bounded source collector and its structured finding model, plus rendered audits for selected templates. Enforce approved hosts, redirects, sitemap children and URL budgets outside the crawler. Adapt its baseline format with coverage and changed-detail checks: its current comparator matches ID/URL but cannot tell a resolved finding from an unvisited page. [Baseline comparator](https://github.com/nurkamol/seo-audit/blob/b70b3bf8f29bcbbdcdfb969079fd41097d1368e1/src/baseline.mjs#L17-L68).

**What Solvd adds.** Owner-approved public-page inventory, intended bots/indexability/canonicals/exclusions, source/render differences and template-level regression tracking. Lighthouse's crawlability score can pass if at least one known bot is allowed, and its structured-data audit is manual. Preserve bot-specific evidence and outstanding checks. [Bot-specific semantics](https://github.com/GoogleChrome/lighthouse/blob/1a4ffa418258919adbbf6ccca548c02e0092bafd/core/audits/seo/is-crawlable.js#L180-L217), [manual structured-data audit](https://github.com/GoogleChrome/lighthouse/blob/1a4ffa418258919adbbf6ccca548c02e0092bafd/core/audits/seo/manual/structured-data.js#L7-L32).

**First proof.** An intended public page accidentally noindexed, an intentionally excluded page, a JavaScript-altered canonical and an unvisited page from a prior baseline. AI can explain the observed mismatch and proposed correction. Rankings, indexing and AI citations need separate evidence. A bounded first crawl is smaller; reliable customer intent and authenticated Search Console interpretation take more work.

## 8. Tracking & Consent QA

**How the implementations differ.** tracking-auditor implements pre-choice/accept/reject execution and vendor payload parsing. Adwize separates a collected snapshot, deterministic checks and an optional actual LLM analyst. OpenWPM is a deeper instrumented Firefox collection framework with visit/command completion and request/POST correlation. [tracking-auditor collection](https://github.com/mbaersch/tracking-auditor/blob/6cacbcc97d706091a74a25105148761c60a1521b/audit.js#L811-L837), [Adwize runner](https://github.com/Adwize/adwize-audit/blob/fe5661b5e4ed7dd6d764242ff1ec48157e5475ff/core/audit.py#L1-L77), [OpenWPM POST collection](https://github.com/openwpm/OpenWPM/blob/4f81c3a94b80b6db0e7393d0700e72f4abf3bc80/Extension/src/background/http-instrument.ts#L296-L343).

**What to adopt.** Build a small Playwright runner for approved states and event expectations, adapting licensed signal/check patterns from Adwize where useful. Its default accepts consent, shares context and lacks the required per-state event-payload assertions, so its public runner is not a complete starting service. Set `analyze=False` unless model use is explicitly approved; its default analyst can send collected evidence to OpenAI when a key exists. Set consent behavior explicitly too. OpenWPM is an alternative if the engagement needs its extra instrumentation. tracking-auditor has no license file in the inspected complete tree; retain it as a comparison and obtain terms before copying code. [Adwize defaults](https://github.com/Adwize/adwize-audit/blob/fe5661b5e4ed7dd6d764242ff1ec48157e5475ff/core/collectors/crawl.py#L126-L164), [analyst input and invocation](https://github.com/Adwize/adwize-audit/blob/fe5661b5e4ed7dd6d764242ff1ec48157e5475ff/agents/analyst/agent.py#L52-L125), [tracking-auditor package](https://github.com/mbaersch/tracking-auditor/blob/6cacbcc97d706091a74a25105148761c60a1521b/package.json#L1-L13).

**What Solvd adds.** The customer's expected event names/triggers, required and forbidden properties, counts/windows and permitted destinations in each consent state. Keep isolated profiles, state transitions, POST/batch parsing, redaction and browser-send versus downstream-receipt evidence. Interpret allowed cookieless behavior against the agreed expectation. AI explains violations of that contract; it should not invent the tracking design or issue a legal determination.

**First proof.** A duplicate event, missing required property, permitted denied-state ping, prohibited destination and incomplete observation window. Enumerate permitted synthetic interactions and label/filter their traffic. Exclude arbitrary checkout and service-worker changes from the default runner. This role requires more original assertion work than the detector-heavy roles; the inspected projects do not supply the customer's contract.

## 9. Mobile Release Readiness

**How the implementations differ.** Greenlight parses source settings and supplied APK/AAB/IPA archives and applies heuristics. Official bundletool dumps AAB manifests/config and validates bundle structure locally. fastlane supplies authenticated Apple/Google clients as well as broad release automation. [Greenlight archive inspection](https://github.com/RevylAI/greenlight/blob/fcb36e395bd4ae20448f2535382baecba9396fd9/internal/playscan/archive.go#L39-L100), [bundletool dump](https://github.com/google/bundletool/blob/586a43a450712a1067f3d92cf7574dee68226302/src/main/java/com/android/tools/build/bundletool/commands/DumpManager.java#L52-L87), [bundletool validation](https://github.com/google/bundletool/blob/586a43a450712a1067f3d92cf7574dee68226302/src/main/java/com/android/tools/build/bundletool/commands/ValidateBundleCommand.java#L72-L92).

**What to adopt.** Prefer official AAB extraction, explicit module coverage and narrowly selected Greenlight parsers where they fill a gap. Separate its local inspection from cloud `verify`, which can register/upload/run builds. Keep platform requirements in a dated, reviewed rule catalog: Greenlight's linked deadlines are hardcoded, not live policy retrieval. [Cloud verification path](https://github.com/RevylAI/greenlight/blob/fcb36e395bd4ae20448f2535382baecba9396fd9/internal/verify/runner.go#L366-L412), [policy constants](https://github.com/RevylAI/greenlight/blob/fcb36e395bd4ae20448f2535382baecba9396fd9/internal/playscan/rules.go#L12-L48).

For optional store observations, use exact GET endpoints or proven client methods. fastlane's older Android readers create/delete an edit transaction; its newer `track_release_summaries` path calls the direct list API without opening an edit. Availability in a compatible release and actual account permissions still require validation. Preserve lifecycle state rather than interpreting a returned version as ready. [Legacy readers](https://github.com/fastlane/fastlane/blob/f6f8c179668f5c476f2fa81857eef6cd27a3a0b2/supply/lib/supply/reader.rb#L3-L48), [direct reader](https://github.com/fastlane/fastlane/blob/f6f8c179668f5c476f2fa81857eef6cd27a3a0b2/supply/lib/supply/reader.rb#L51-L64), [official GET endpoint](https://developers.google.com/android-publisher/api-ref/rest/v3/applications.tracks.releases/list).

**What Solvd adds.** An app/platform/channel requirement-to-evidence matrix linking source revision, exact artifact digest, module/ABI coverage, supplied build/signing lineage, store observations, deadlines, actual extension evidence and accountable next action. AI can draft this explanation from approved rules and observations. Parsed metadata alone cannot establish signature, source lineage, successful device behavior or store acceptance.

**First proof.** A supplied artifact with known metadata, mismatched source/artifact identity, missing build validation and a requirement that applies only to a particular channel. Static extraction is smaller; current policy interpretation, signed-build lineage and store-access variations make the complete role a more substantial build.

## Shared work to build once

Keep this limited to what the first two workflows actually need, then extend it:

1. **Approved inputs and checks.** Application/environment, scope revision, allowed targets/actions, expected outcomes, supplied evidence and missing prerequisites.
2. **Run record.** Target/revision or artifact digest, observation time, engine/browser/configuration versions, attempt history, native results, raw evidence links/hashes and coverage. Keep role-specific data rather than flattening every result into a score.
3. **Comparable history.** An explicitly accepted baseline; new, unchanged, uncertain, accepted and verified findings; exclusions with owner/reason/expiry. An absent check or incompatible run cannot resolve a finding.
4. **Bounded AI interpretation.** Approved evidence extracts, linked claims, tool/time/cost limits and preserved deterministic output if the model fails. Investigation permissions differ from browser test actions and output permissions.
5. **Reviewed report and verification.** Private draft, named reviewer, owner and next action; separate controlled publication. Repairs are rechecked against the relevant accepted contract. Urgent native alerts continue independently.

These are implementation requirements inferred from the inspected gaps. They are not claims that a shared Solvd maintenance platform already exists. The internal Cascade work provides runtime patterns; its previous narrow execution proof does not establish scheduling, semantic accuracy or cost across these 9 workflows.

## Build and validation sequence

Retain the previously recorded code/change → dependency → integration → SEO → performance → analytics progression as the planning starting point. The following is a proposed refinement for the current 9-role library, subject to selecting a real pilot app:

1. **Small source-evidence slice:** M4 supplied-diff review and M2 supplied-inventory review, using the same intake, raw evidence and reviewed report. Add a deliberately stale/missing result before adding more features.
2. **Small browser-evidence slice:** M3 one approved journey with downstream readback, then M7 selected public templates. Reuse the browser setup for M6 while retaining distinct accessibility outcomes.
3. **Measurement and event slices:** M5 in an isolated performance lane; M8 with an owner-approved event/consent contract. The same browser tooling does not mean simultaneous performance collection or a shared consent profile.
